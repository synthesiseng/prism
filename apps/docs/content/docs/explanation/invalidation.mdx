---
title: Invalidation
description: Tell Prism when app-owned data or surface state needs another paint pass.
---

Prism owns the paint lifecycle, but your app owns the state that changes what should be drawn.

Invalidation schedules paint; it is not app state management.

Prism invalidates automatically when a surface is registered or unregistered, when `onPaint()` registers a paint handler, and when `surface.setBounds()` changes bounds outside an active paint pass.

During paint, native size changes defer drawing until a fresh browser snapshot after the handler pass completes. Fallback bounds changes retain work for the next runtime frame. A stopped fallback runtime needs `start()` or an explicit `paintOnce()` to consume that work.

**Alpha.10 candidate:** a native position change after drawing requests a following paint without layout preparation. Unchanged literal bounds are a no-op, except when an outside-paint call restarts a stopped layout episode.

Call `runtime.invalidate()` when app-owned state changes and Prism would not otherwise know that another paint pass is needed.

Call the invalidation API from paint handlers when another runtime-owned pass is needed:

```ts
runtime.onPaint(({ drawSurface, invalidate }) => {
  drawSurface(surface);

  if (animationStillRunning) {
    invalidate();
  }
});
```

Keep app state outside Prism. Use invalidation to schedule painting, not to store application data.

In the alpha.10 candidate, after layout retry exhaustion, fix the layout and call `setBounds()` or `invalidate()` outside paint to recover. Repeated calls inside paint do not reset the retry limit. See [paintOnce()](/docs/explanation/paint-once).
